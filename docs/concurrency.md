# 并发处理实现说明

## 目标

服务端仍保持“一条连接内请求、响应顺序一致”的第一版协议，同时允许不同客户端的
登录、目录访问、文件传输和预览任务并行执行。任何队列满载都应拒绝新任务，而不是
继续创建线程或无限保留请求数据。

## 当前实现

- `TaskExecutor` 是固定大小、有界队列的工作执行器；服务端连接工作池大小为
  `min(8, max(2, CPU 核数 × 2))`，等待队列最大 64 个连接；
- 监听线程只负责接收连接，再将整条连接交给连接工作池。每条连接仍在同一工作任务中
  顺序执行“接收报文 → 处理 → 发送响应”，所以不会改变 requestId 回显及现有同步客户端；
- PDF、视频、DOCX/PDF 转 Markdown 等会启动外部工具的操作进入独立预览执行器，最多
  同时运行 2 个，等待队列最大 16 个。满载时返回 `SERVER_BUSY`；
- 上传以 `transferId` 对应的互斥锁保持同一传输的偏移顺序。写入 `.part` 和最终 SHA-256
  复核不再持有仓库的全局元数据锁；不同传输可并行进行磁盘 I/O；
- 下载读取 blob 时先复制传输状态，文件读取在全局元数据锁外进行，结束时再短暂回收
  下载会话。

## 一致性边界

SQLite 元数据目前仍使用一个连接及短时全局锁，因此节点、配额、引用计数和上传会话的
数据库更新仍是串行的。这是有意保留的安全边界：不能在单个 SQLite 连接上直接把原来的
`mutex_` 改成读写锁，否则会引入未定义的并发访问。

下一阶段若要继续提升目录/登录吞吐，应将 `CloudRepository` 改为“只读连接池 + 单写入
队列”，并为每个连接设置 `busy_timeout`；写入操作仍必须用事务提交。该迁移会改变存储层
资源生命周期，需先补充多客户端压力测试后再进行。

## 建议验证

1. 20 个客户端同时注册/登录/列根目录；
2. 两个账号分别上传不同的大文件，并验证进度能同时推进；
3. 同一账号重复发送同一 `transferId` 的块，验证偏移错误被拒绝；
4. 同时触发 3 个 PDF/视频预览，验证前 2 个执行，第 3 个排队或在队列满时收到
   `SERVER_BUSY`；
5. 在传输和预览进行中重启服务端，确认 `.part`、上传会话和数据库仍可恢复。
