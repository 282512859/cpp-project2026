## 二、整体架构

本项目采用“**元数据与文件内容分离**”的设计。

### 1. 数据库保存元数据

SQLite 数据库中保存：

- 用户信息
- 文件和目录名称
- 父目录关系
- 文件大小
- 文件哈希
- 文件引用次数
- 上传进度
- 分享码
- 用户配额和已使用空间

### 2. 文件系统保存真实内容

服务器磁盘保存真实文件：

```text
storage/
├── temp/     上传中的临时文件
└── blobs/    上传完成后的正式文件
```

数据库中的 `nodes` 表只保存文件节点信息，真正的文件内容保存在 blob 文件中。

这样做的好处是：

- 数据库不会直接存储大文件；
- 文件内容可以通过 SHA-256 去重；
- 多个文件节点可以引用同一个 blob；
- 数据库和文件系统各自负责适合自己的工作。

## 三、数据库设计

### 1. users 表

保存用户相关信息：

- 用户 ID
- 用户名
- 密码哈希
- 随机盐
- 用户配额
- 已使用容量
- 注册时间

密码不保存明文，而是保存密码哈希。

### 2. nodes 表

`nodes` 表表示用户看到的目录树。

重要字段包括：

- `id`：节点 ID
- `owner_id`：所属用户
- `parent_id`：父目录 ID
- `name`：文件或目录名称
- `is_directory`：是否为目录
- `blob_id`：对应的文件内容
- `size`：文件大小
- `modified_at`：修改时间

目录和文件都使用节点表示：

```text
目录：
is_directory = 1
blob_id = NULL

文件：
is_directory = 0
blob_id 指向 blobs 表
```

### 3. blobs 表

`blobs` 表保存文件内容的索引：

- 文件 SHA-256
- 文件大小
- 实际相对路径
- 引用次数
- 创建时间

`ref_count` 表示有多少个文件节点正在引用这个 blob。只有当 `ref_count` 降为 0 时，服务器才会删除实际文件。

### 4. upload_session 表

这个表用于支持断点续传，保存：

- 上传任务 ID
- 用户 ID
- 目标父目录
- 文件名
- 文件哈希
- 预期大小
- 已接收大小
- 临时文件路径
- 创建时间
- 过期时间

如果上传中断，客户端重新上传时可以根据这些信息继续传输。

## 四、目录树的实现

### 1. `parent_id` 的作用

项目使用 `nodes` 表加 `parent_id` 表示目录关系。

例如：

```text
根目录 0
├── 文档
│   └── 课程论文.docx
└── 图片
    └── photo.jpg
```

数据库中可以表示为：

```text
文档.parent_id = 0
图片.parent_id = 0
课程论文.docx.parent_id = 文档.id
photo.jpg.parent_id = 图片.id
```

`parent_id = 0` 表示根目录。

### 2. 查询目录

`list(userId, parentId)` 只查询指定目录的直接子节点，而不会一次性返回整个目录树：

```sql
WHERE owner_id = ?
AND parent_id = ?
```

这样可以避免查询结果过大，并允许客户端逐级进入目录。

### 3. 创建目录

`mkdir()` 的主要流程是：

1. 验证目录名称；
2. 检查父目录是否存在；
3. 检查父节点是否确实是目录；
4. 向 `nodes` 表插入新目录；
5. 如果同一父目录下存在同名节点，则返回冲突错误。

数据库使用 `UNIQUE(owner_id, parent_id, name)` 防止同一个目录下出现同名文件或目录。

### 4. 删除目录

删除目录时不能只删除一条记录，因为目录下面可能还有多级子目录。

项目使用递归 CTE 找到整个子树：

```sql
WITH RECURSIVE tree AS (...)
```

删除流程是：

1. 找到目标节点；
2. 递归找到所有子节点；
3. 收集所有被引用的 blob；
4. 删除这些节点；
5. 减少 blob 的引用次数；
6. 减少用户的已使用空间；
7. 删除引用次数为 0 的物理文件。

## 五、文件上传实现

文件上传由三个阶段组成。

### 1. `beginUpload()`

客户端首先发送文件名、文件大小、SHA-256 和父目录 ID。

服务器先完成以下检查：

1. 文件大小不能为负数；
2. 文件名必须合法；
3. 父目录必须存在；
4. 当前目录不能有同名文件；
5. 用户配额必须足够；
6. 是否已经存在相同内容；
7. 是否存在可恢复的上传会话。

### 2. `appendUpload()`

客户端不会一次性发送整个文件，而是分块上传。每一块数据都会携带上传任务 ID、当前偏移量和数据内容。

服务端检查：

```text
客户端 offset == 服务端 received
```

如果不相等，就拒绝这次写入，防止重复写入、数据块乱序和网络重试导致文件内容错位。

数据首先写入：

```text
storage/temp/xxx.part
```

同时更新内存中的接收进度、数据库中的 `received` 和上传会话的过期时间。

### 3. `finishUpload()`

上传完成后，服务器会重新计算临时文件的 SHA-256，而不是直接相信客户端。

只有满足以下条件才会提交：

- 实际接收大小等于预期大小；
- 临时文件哈希等于客户端声明的哈希；
- 用户配额仍然足够；
- 数据库操作成功。

之后服务器会：

1. 如果相同 blob 已存在，删除临时文件并复用已有 blob；
2. 如果不存在，将 `.part` 文件移动到正式 blob 路径；
3. 写入 `blobs` 表；
4. 增加 `ref_count`；
5. 创建 `nodes` 文件节点；
6. 增加用户 `storage_used`；
7. 删除上传会话；
8. 提交事务。

## 六、文件夹上传实现

项目不是把整个文件夹压缩成一个文件上传，而是递归创建远程目录，再逐个上传其中的文件。

客户端的 `doUploadDirectory()` 工作流程是：

1. 统计文件夹内所有普通文件的总大小；
2. 在服务器创建根目录；
3. 遍历当前目录；
4. 遇到子目录，递归调用上传函数；
5. 遇到普通文件，调用单文件上传接口；
6. 根据所有文件的完成情况更新总进度。

例如本地目录：

```text
project/
├── docs/
│   └── readme.txt
└── src/
    └── main.cpp
```

远端执行顺序大致是：

```text
mkdir(project)
mkdir(project/docs)
upload(readme.txt)
mkdir(project/src)
upload(main.cpp)
```

这样既能完整保留目录结构，又能让每个文件独立支持秒传、断点续传、哈希校验和配额检查。

## 七、秒传和文件去重

秒传的核心是 SHA-256。

上传开始时，客户端先发送文件大小和 SHA-256。服务端在 `blobs` 表中查询：

```sql
WHERE sha256 = ?
AND size = ?
```

如果已经存在相同文件，服务端不再接收文件内容，而是：

1. 增加 blob 的 `ref_count`；
2. 创建一个新的 `nodes` 文件节点；
3. 增加用户的存储占用；
4. 直接返回节点 ID。

秒传并不是不创建文件记录，而是不重复传输和保存物理内容，只新增一个逻辑引用。

## 八、文件下载实现

### 1. `beginDownload()`

服务端先验证用户是否登录、文件节点是否存在、文件是否属于当前用户，以及节点是否确实是普通文件。

然后生成下载传输 ID，并在内存的 `downloads_` 中保存用户 ID、blob 文件路径和文件大小。

### 2. `readDownload()`

客户端每次发送下载传输 ID、当前偏移量和最大读取字节数。服务端从 blob 文件中读取指定范围的数据并返回二进制数据，避免一次性将大文件全部加载到内存中。

## 九、文件预览与存储模块的关系

文件预览主要由 `ServerApp` 调度，但存储模块提供关键支持。

服务端通过：

```cpp
repository_.getStoredFile(userId, nodeId)
```

获得文件名称、文件大小和 blob 的真实路径。

之后：

- 文本文件读取前一部分内容；
- 图片读取二进制；
- PDF 转换成页面图片；
- 视频生成 GIF 预览；
- DOCX/PDF 转换为 Markdown 或文本。

成员2负责安全地定位文件，并保证只能访问当前用户拥有的文件；具体预览界面由客户端负责显示。

## 十、配额管理

每个用户都有：

```text
quota
storage_used
```

上传文件时检查：

```text
storage_used + file_size <= quota
```

删除文件时释放对应容量：

```text
storage_used -= deleted_size
```

配额更新必须和文件节点、blob 引用更新处于同一个事务中，否则可能出现文件已经创建但空间没有增加，或文件已经删除但空间没有释放的问题。

## 十一、事务和锁

### 1. `std::mutex`

`CloudRepository` 中的 `std::mutex mutex_` 用于保护 SQLite 连接、`uploads_`、`downloads_`、上传状态以及文件操作与数据库状态之间的协调。

普通接口进入时使用：

```cpp
std::lock_guard lock(mutex_);
```

### 2. 上传任务锁

每个上传任务还有一个独立的 `ioMutex`，作用是保证同一个上传任务不能同时写入两个数据块，同时允许不同上传任务并行进行。

### 3. SQLite 事务

完成上传时，需要同时修改 `blobs`、`nodes`、`users` 和 `upload_session`。这些操作使用：

```sql
BEGIN IMMEDIATE
...
COMMIT
```

如果中间任何一步失败，就执行：

```sql
ROLLBACK
```

这样可以保证要么所有数据库修改成功，要么全部撤销。

## 十二、安全设计

### 1. SQL 注入防护

项目使用带参数的预处理语句：

```cpp
Statement query(db_, "SELECT ... WHERE username=?");
query.text(1, username);
```

而不是拼接 SQL 字符串。

### 2. 用户权限校验

大多数查询都会带上：

```sql
WHERE owner_id = ?
```

因此用户不能只凭一个 `nodeId` 访问其他用户的文件。

### 3. 文件名校验

文件名会经过 `validateName()` 检查，防止空文件名、路径穿越、非法字符、特殊目录名和超长名称。

### 4. 哈希校验

上传完成后服务端重新计算 SHA-256，防止传输数据损坏，以及客户端声明内容与实际内容不一致。

### 5. 密码保护

基础实现使用随机盐和哈希保存密码。加固副本中进一步使用 PBKDF2-HMAC-SHA-256，通过多轮计算提高离线暴力破解成本。

需要注意：当前工程中同时保留了原始实现和 `CloudRepository_hardened.cpp` 加固副本，正式答辩前需要确认 CMake 实际编译的是哪个文件，不能只根据加固副本存在就声称默认构建已经启用。

## 十三、我的模块亮点

1. **元数据和物理文件分离**：避免把大文件直接存进 SQLite，提升大文件处理能力。
2. **基于哈希的去重**：相同内容只保存一份，减少磁盘占用，并支持秒传。
3. **支持断点续传**：上传中断后可以从已接收偏移继续，不需要重新上传整个文件。
4. **目录树设计清晰**：通过 `parent_id` 建立树形关系，支持递归目录、批量删除和文件夹上传。
5. **数据库事务与文件操作结合**：同时考虑数据库回滚和物理文件清理，避免产生孤儿文件。
6. **并发控制较完整**：通过仓库锁、上传任务锁和 SQLite 事务控制并发访问。

## 十四、完整口播稿

老师好，我负责的是项目中的服务端存储模块。

我的模块主要使用 C++、SQLite 和文件系统实现。整体设计采用数据库保存元数据、文件系统保存真实内容的方式。数据库主要保存用户、目录节点、文件哈希、文件大小、上传进度和分享码等信息，真实文件则保存在服务器的 blob 目录中。

在目录管理方面，我使用 `nodes` 表统一表示目录和文件，并通过 `parent_id` 建立树形关系。`parent_id` 为 0 时表示根目录，其他值表示父目录节点。这样可以支持目录列表、创建目录、重命名、递归删除和文件夹上传。

在文件上传方面，系统把上传分为初始化、分块传输和完成提交三个阶段。初始化时会检查文件名、文件大小、父目录、用户配额和文件哈希。如果相同文件已经存在，系统会直接增加 blob 的引用次数，实现秒传。如果文件没有上传完成，则会复用上传会话，实现断点续传。

分块上传的数据首先写入临时文件。上传完成后，服务端会重新计算文件的 SHA-256，并和客户端提供的哈希进行比较。校验成功后，文件才会被移动到正式 blob 目录，并在数据库中创建文件节点。数据库更新过程使用事务，如果中间发生错误，就回滚数据库操作并清理临时文件。

文件夹上传并没有被当作一个整体文件处理，而是由客户端递归遍历本地目录，先调用 `mkdir` 创建远程目录，再对每个普通文件调用单文件上传接口。这样既能保持原有目录结构，又可以让每个文件独立支持秒传、断点续传和哈希校验。

在下载和预览方面，服务端先根据用户 ID 和节点 ID 验证访问权限，再定位真实 blob 文件。下载采用分块读取，预览则根据文件类型读取文本、生成图片、渲染 PDF 或生成视频缩略图，最后由客户端界面负责显示。

在并发控制方面，`std::mutex` 用于保护数据库连接和内存中的上传、下载状态，每个上传任务还拥有独立的 I/O 锁。涉及多个表的操作则使用 SQLite 事务，保证节点、blob、用户配额和上传状态能够保持一致。

这个模块的核心目标是保证文件数据的安全性、完整性和一致性。也就是说，用户看到的是目录树，服务器管理的是元数据和 blob 文件，而所有上传、下载、分享、预览和删除操作最终都要经过服务端存储层校验。

## 十五、老师可能追问的问题

### 问题1：为什么不直接把文件存到 SQLite？

答：大文件直接存进 SQLite 会使数据库体积快速膨胀，也不利于文件流式读写和备份。因此项目采用数据库存元数据、文件系统存 blob 的方式。数据库负责管理关系，文件系统负责保存内容。

### 问题2：为什么使用 SHA-256？

答：SHA-256 可以为文件生成内容指纹，用于完整性校验和去重。上传完成后服务器会重新计算哈希，不能只相信客户端传来的值。

### 问题3：秒传是否意味着不创建文件记录？

答：不是。秒传时不会重复上传和保存物理内容，但仍然会创建新的 `nodes` 节点，并增加 blob 的 `ref_count`。

### 问题4：删除目录时如何删除子文件？

答：使用递归查询找到整个子树，删除所有节点，并减少这些节点引用的 blob 的引用次数。只有引用次数为 0 时，才删除实际文件。

### 问题5：为什么需要 `parent_id`？

答：`parent_id` 用来表示节点属于哪个目录。它把所有目录和文件组织成一棵树，同时避免为每个目录单独建表，查询和递归删除都比较方便。

### 问题6：为什么既有 mutex 又有数据库事务？

答：两者解决的问题不同。`mutex` 保护 C++ 对象、SQLite 连接和内存 map 的并发访问；数据库事务保证多条 SQL 修改要么全部成功，要么全部失败。

### 问题7：上传失败会不会留下垃圾文件？

答：正常流程中，上传内容先写入临时文件。失败时会清理上传状态和临时文件。正式 blob 移动后如果数据库提交失败，也需要删除未被引用的物理文件，避免产生孤儿 blob。

### 问题8：用户能不能通过修改 nodeId 读取别人的文件？

答：不能。服务端查询文件时会同时检查 `node_id` 和 `owner_id`，只有当前登录用户拥有的节点才能访问。

### 问题9：文件夹上传是一条请求完成的吗？

答：不是。客户端递归遍历目录，目录通过 `mkdir` 创建，文件通过独立的分块上传流程传输。这样可以保留目录结构，并支持单文件级别的断点续传和秒传。

### 问题10：PBKDF2 是否已经在正式构建中启用？

答：项目中已经有 PBKDF2 的加固实现，用于新密码哈希和旧哈希登录后的升级。但当前代码中同时保留了原始实现和 `CloudRepository_hardened.cpp` 加固副本，正式答辩前需要确认 CMake 实际编译的是哪个文件，不能只根据加固副本存在就声称默认构建已经启用。
